# 从 `python app.py` 看懂 Linux 进程与内存

我们在实际项目的开发过程中，通常会遇到一些问题：当 Agent 调用工具后卡住、内存持续增长，或者任务突然退出时，进程与内存的基础知识能帮助我们判断问题发生在哪里。

本文从终端里的一条命令出发，串起进程的创建、运行、内存使用和退出，并用一个小实验观察这些概念。

## 一、按下回车后，发生了什么？

假设我们在 Shell 中输入：

```bash
python app.py
```

一种典型的执行过程是：

1. Shell 解析命令，找到 Python 解释器。
2. Shell 通过 `fork()` 创建子进程。此时父进程和子进程有不同的 PID（进程 ID）。
3. 子进程调用 `execve()`，把自己运行的程序替换为 Python 解释器。**它的 PID 不会因此改变。**
4. Python 解释器读取 `app.py`，执行其中的代码。
5. Shell 等待子进程结束，取得退出状态，再显示命令提示符。

可以用一句话记住：**`fork()` 创建进程，`execve()` 更换这个进程运行的程序。** 不同 Shell 和执行场景可能采用其他启动方式，但这条过程足以建立基本模型。这里被 Linux 启动的可执行程序是 Python 解释器；`app.py` 是解释器随后读取的文件。

```text
Shell（父进程）
  └── Python（子进程，执行 app.py）
```

## 二、虚拟地址不等于物理内存

每个进程都有自己的**虚拟地址空间**。程序读写的是虚拟地址；CPU 根据该进程的页表找到相应的物理内存页。同一个虚拟地址在两个进程中，可以对应不同的物理内存。

进程的地址空间里，通常有程序代码、栈、动态分配的内存，以及映射的文件或共享库。以 Python 代码为例：

```python
x = [1, 2, 3]
```

Python 会创建列表对象，并让 `x` 引用它。Python 的内存分配器管理对象所用的小块空间；需要更多空间时，再向操作系统申请。因此，创建一个列表并不意味着内核要为这个列表单独分配一块物理内存。

更重要的是，**获得一段虚拟地址范围，不代表这段范围已全部占用物理内存**。进程首次访问某个尚未准备好的页面时，CPU 会触发缺页异常。内核检查地址是否有效：如果有效，就准备页面、建立映射，让程序继续运行；如果访问非法，进程可能收到导致“段错误”的信号。缺页异常本身是正常机制，并不等于程序崩溃。

这也是查看内存指标时要区分的两件事：

| 指标         | 表示什么                                         |
| ------------ | ------------------------------------------------ |
| VSZ / VmSize | 进程的虚拟地址空间规模                           |
| RSS / VmRSS  | 当前驻留在物理内存中的页面规模，可能包含共享页面 |

## 三、为什么 `fork()` 不必复制全部内存？

`fork()` 创建子进程后，父子进程最初可以共享已有的物理内存页。只有某一方尝试修改共享页时，内核才复制相应的页，让双方各自拥有修改后的内容。这叫**写时复制**（copy-on-write）。

```text
刚 fork：       父进程 ─┐
                       ├─ 共享的物理页
                子进程 ─┘

子进程修改后： 父进程 ── 原来的页
                子进程 ── 新复制的页
```

在前面的命令中，子进程很快执行 `execve()`，把原来的程序内存布局换成 Python 的布局。因此，没有必要在 `fork()` 时把 Shell 的所有物理内存页完整复制一遍。

## 四、进程存在，不代表它一直在用 CPU

进程可以正在运行、已准备好运行但在等 CPU，也可以因等待网络、磁盘或其他事件而暂时不能继续。Linux 的 `ps` 输出中，常见的状态有：

| 状态 | 简化理解                         |
| ---- | -------------------------------- |
| `R`  | 正在运行，或已就绪、等待 CPU     |
| `S`  | 正在等待某个事件，之后可以被唤醒 |
| `Z`  | 已退出，父进程尚未领取退出状态   |

例如，`app.py` 发出网络请求后等待服务器回复，它仍是一个存在的进程，但这段时间不需要持续占用 CPU。于是，一个程序运行了十秒、CPU 使用率却很低，并不矛盾。

## 五、进程结束后，为什么还能看到 `Z`？

Python 程序结束时，内核释放它的大部分资源，同时暂时保留 PID 和退出状态，供父进程读取。父进程调用 `wait()` 一类的系统调用后，这条记录才被清理。在“子进程已退出、父进程尚未领取结果”的间隙，子进程显示为**僵尸进程**（`Z`）。它已经不再执行代码，也不再保有原来程序的大部分内存。

这里有两个不同的“等待”：进程**等待网络**时仍在运行生命周期中；父进程调用 **`wait()`** 是为了领取子进程的退出结果。

## 六、一个案例

把下面的代码保存为 `memory_demo.py`，在一个终端运行：

```python
import mmap
import os

size = 64 * 1024 * 1024
memory = mmap.mmap(-1, size)
print(f"PID: {os.getpid()}")
input("已申请 64 MiB 虚拟内存；按回车逐页写入...")

for offset in range(0, size, mmap.PAGESIZE):
    memory[offset] = 1

input("已逐页写入；按回车退出...")
```

在另一个终端，把 `<PID>` 换成程序打印的数字，在两次暂停处分别运行：

```bash
ps -o pid,ppid,stat,vsz,rss,comm -p <PID>
```

我在 Linux 环境中做同类实验，得到以下读数。具体数值会因 Python 版本和系统环境而不同：

| 时刻                     | 状态 |    VmSize |     VmRSS |
| ------------------------ | ---- | --------: | --------: |
| 申请 64 MiB 后，尚未写入 | `S`  | 90,084 kB |  9,588 kB |
| 逐页写入后               | `S`  | 90,084 kB | 75,124 kB |

VmSize 在申请时已经增加；逐页写入后，它基本不变，而 VmRSS 增加了 **65,536 kB，也就是 64 MiB**。两次都是 `S`，因为程序正在等待终端输入。这个实验直接展示了“获得地址空间”和“实际占用物理页”的区别。

再用 `free -h` 查看系统整体内存。一次实际观察得到：

```text
               total   used   free   buff/cache   available
Mem:            12Gi  6.1Gi  2.2Gi        4.7Gi       6.8Gi
```

`free` 只有 2.2 GiB，不代表程序只能再使用 2.2 GiB。Linux 会用内存缓存文件等数据，许多缓存可在需要时回收；`available` 是更有参考价值的可用内存估计。也不能把所有进程的 RSS 简单相加当作系统的 `used`：进程可能共享页面，内核和缓存也会使用内存。

假设 `agent.py` 启动子进程 `analyze.py` 处理文件。Agent 等结果时可能处于 `S` 状态，CPU 使用率很低；`analyze.py` 如果把巨大文件一次读入内存，RSS 则可能持续上涨。系统内存紧张时，内核可能终止子进程。Agent 随后领取它的退出状态，得知任务异常结束。

如果退出状态表明子进程收到了 `SIGKILL`，不能只凭这一点断定是内存不足：其他原因也能发送同样的信号。应结合当时的 RSS、系统可用内存和内核日志判断。

排查这类问题，先分别回答三个问题：**进程还在吗？它是在用 CPU 还是在等待？它的 RSS 和系统可用内存如何变化？** 这三个问题，正是 Linux 进程与内存基础知识在实际开发中的用处。
