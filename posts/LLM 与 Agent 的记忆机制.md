# Agent 的记忆系统：从上下文到可检索状态

用户曾经说过“不要在周五安排会议”，一个月后 Agent 却又把会议定在周五。这类问题常被简化为“模型忘了”，但失败可能发生在任何一环：

- 系统当时没有写入这条偏好；
- 写入了，但保存在错误的用户或作用域下；
- 检索时没有找到；
- 找到了，却在上下文裁剪中被丢弃；
- 模型看到了，但新指令或更高优先级约束与它冲突；
- 这条偏好早已失效，系统却仍在使用。

因此，Agent 记忆不是“接一个向量库”就完成的功能。它是一条完整的信息生命周期：

> **从经验中选择值得保留的信息，在正确的时间和作用域中取回，用它改变当下行为，并能在过期、冲突或用户要求时更正与删除。**

## 模型“知道”不等于 Agent “记得”

对一次普通的模型 API 调用，可以把输入输出简化为：

```text
tokens_in → model → tokens_out
```

请求结束后，模型不会因为刚才的对话自动改写权重。下一次调用之所以看起来能接着聊，通常是应用重新提供了对话历史或可恢复的响应状态。

容易被都称为“记忆”的东西，至少有五类：

| 层次 | 保存什么 | 典型生命周期 | 是否可由应用直接编辑 |
| --- | --- | --- | --- |
| 模型权重 | 训练得到的语言模式与世界知识 | 跨请求，直到模型更新 | 否 |
| 解码状态 / KV cache | 当前序列的中间计算 | 通常限于一次生成或服务会话 | 否 |
| 模型上下文 | 本次推理可见的指令、对话与工具结果 | 一次请求 | 是，通过组装输入 |
| 会话历史 | 原始消息、工具调用与轨迹 | 一次任务或会话 | 是 |
| 外部记忆 | 用户偏好、任务事实、历史经验与业务对象 | 可跨会话 | 是 |

权重中的知识不是某个用户的私有记忆；KV cache 也不是可搜索、可删除的长期存储。Agent 工程中所说的“记忆系统”，主要指后三层之间的协作。

## 不要先按存储技术分类

把记忆分成“向量库记忆”和“数据库记忆”，容易把实现手段误当成产品语义。更有用的分法是看信息如何影响行为。

### 工作记忆：当前任务正在发生什么

例如：

- 当前目标、子任务和进度；
- 最新观察与工具返回；
- 待确认的用户选择；
- 预算、权限、重试次数和锁。

它对时效性要求高，通常由运行时状态和当前上下文承载，不宜依赖语义搜索“大概找回来”。

### 情节记忆：某次经历了什么

例如：

- 上次部署为什么失败；
- 用户曾经验证过哪个方案；
- 某个工具在什么参数下返回过什么。

情节记忆通常带有时间、任务、轨迹和来源。它适合帮助 Agent 避免重复探索，但过去成功不能直接被当作当前环境仍然成立的证据。

### 语义记忆：目前认为成立的事实

例如：

- 用户偏好使用中文；
- 项目的默认分支是 `main`；
- 某个服务属于哪个团队。

语义记忆强调去重、更新和冲突解决。它不应只是一堆相似句子，而应能表达“新事实取代了旧事实”。

### 程序记忆：这类任务应该怎样做

例如团队约定、标准流程、工具使用说明和已验证的操作策略。这类信息更适合作为版本化规则或技能，而不是每次从非结构化聊天中猜测。

这四类记忆可以共用存储，也可以分开实现。关键是先区分语义，再选择索引、表结构和检索策略。

## 一条完整的记忆生命周期

```text
观察与对话
     │
     ▼
候选记忆提取
     │
     ▼
写入判断 → 规范化 / 去重 / 定作用域
     │
     ▼
持久化 + 索引
     │
     ▼
按当前任务召回
     │
     ▼
权限过滤 → 排序 → 预算裁剪
     │
     ▼
注入模型上下文
     │
     ▼
观察是否真正被使用
     │
     ▼
更新 / 失效 / 删除
```

这条链上每一步都可能丢失信息或放大错误。因此，记忆质量不能只用向量检索的 Top-K 命中率代表。

## 写入：不是每句话都值得被记住

如果系统把全部对话都当作长期记忆，很快会得到一个充满闲聊、重复、过期信息和错误推断的记忆库。

一条信息值得持久保留，通常是因为它至少满足一项：

- 用户明确要求系统记住；
- 它会稳定地改变未来行为；
- 它是长期任务恢复不可缺少的状态；
- 它记录了一次高价值成功或失败的原因；
- 它是后续必须审计的决策或外部动作。

反之，模型自己的推测、第三方文档中的指令、一次性寒暄和未经确认的敏感属性，不应默认进入长期记忆。

### 记忆条目需要携带上下文

只保存一句“用户不喜欢周五开会”还不够。一条可管理的记忆至少应该表达：

```python
@dataclass
class MemoryRecord:
    id: str
    subject_id: str
    kind: str
    content: str
    scope: str
    source_ref: str
    confidence: float
    created_at: datetime
    valid_from: datetime | None
    valid_until: datetime | None
    status: str
```

- `subject_id` 防止不同用户或项目的记忆串线；
- `scope` 区分全局、组织、项目、任务和会话级记忆；
- `source_ref` 保留它从哪次对话或事件中得来；
- 有效期和 `status` 让系统能够表达过期、撤销和被新事实取代。

`confidence` 只是记忆提取阶段的不确定度，不能替代来源和用户确认。对权限、付款和身份等高风险属性，应查询真实业务系统，不应把记忆库当作权威来源。

## 检索：相似不等于此刻应该使用

向量检索擅长找到语义相似的文本，却不擅长独立处理：

- 精确的用户、项目和权限边界；
- 时间先后与事实有效期；
- 数值、编号、状态枚举等精确匹配；
- 新事实覆盖旧事实的关系；
- 多条记忆之间的逻辑冲突。

所以，成熟的召回过程通常是混合的：

```text
确定 subject + scope + 权限
            ↓
结构化过滤 + 关键词/向量召回 + 时间索引
            ↓
去重、冲突检测与重排
            ↓
按任务相关性、新鲜度、可信度和 token 成本选择
```

对“默认分支名称”这类事实，结构化 key-value 查询比语义检索更可靠；对“过去遇到过类似的部署错误吗”，语义检索更合适。没有一种索引能同时最优地回答所有问题。

## 注入：上下文窗口是预算，不是仓库

外部存储可以很大，模型每次能有效使用的上下文却始终有限。这不只是硬上限问题：即使输入没有超限，大量低相关片段也会稀释关键信号。

因此，上下文组装应先分配预算，再选择内容：

```text
system / policy
+ current user request
+ current task state
+ required tool schemas
+ selected memories
+ recent conversation
+ reserved output budget
≤ model context budget
```

常见的长度控制手段包括：

- 先结构化过滤，不让无权或过期记忆进入候选集；
- 粗召回后重排，只保留对当前决策有价值的片段；
- 将长轨迹转为有来源引用的 checkpoint 或摘要；
- 对精确事实使用紧凑的结构化表示，不重放整段对话；
- 为高优先级指令、当前问题和输出显式预留空间。

重排、压缩和裁剪都不是免费的：重排可能漏掉真正相关的条目，摘要可能改写含义，裁剪可能删除稍后才显示价值的信息。所有策略都需要在真实任务上评测，不能只检查是否没有超 token 上限。

## 更新与遗忘：记忆必须可以变旧

“用户在北京”与“用户现在在上海”可能都曾经为真。如果记忆系统只会追加，不会表达时间与取代关系，检索就会同时返回两个冲突事实。

常见的处理语义有：

- **supersede**：新条目取代旧条目，但保留历史关系；
- **expire**：条目超过有效期，默认不再召回；
- **revoke**：用户或权威数据源明确撤销；
- **delete**：根据用户请求或数据保留政策删除，并处理派生索引与缓存。

向量索引、摘要、备份和观测日志都可能是原数据的派生物。“删除一行数据库记录”不一定等于系统已经忘记，删除路径必须覆盖这些副本。

## 六种比“没检索到”更危险的失败

### 1. 错误写入

模型把猜测当作用户事实，或把第三方文档中的内容当作用户指令保存。错误一旦进入长期记忆，会在多次会话中被重复放大。

### 2. 跨作用域泄漏

用户 A、项目 A 或私有任务的记忆被召回到另一个上下文。权限过滤必须发生在召回早期，且不能只交给模型“自觉忽略”。

### 3. 陈旧事实覆盖当前现实

过去的配置、负责人或用户偏好没有失效。检索分数再高，也不能证明它目前仍为真。

### 4. 记忆中毒与指令注入

被存入的网页、邮件或工具输出可能包含恶意指令。记忆内容应被当作不可信数据，不能因为“已经存在自己的数据库中”就升级为高优先级指令。

### 5. 召回成功，但没有改变行为

只评估检索是否命中，会忽略模型是否真正遵守该记忆。例如偏好已被注入，但排序太靠后、表述含糊或与当前指令冲突，最终行为仍然错误。

### 6. 无法解释记忆从何而来

如果条目没有来源、时间和写入原因，用户无法纠错，开发者也无法区分是提取错误、旧数据还是调试污染。

## 最小可用架构

```text
                 ┌────────────────┐
对话 / 工具结果 ──▶│ Memory Writer  │
                 └───────┬────────┘
                         │ candidates
                         ▼
                 ┌────────────────┐
                 │ Policy / Scope │
                 │ dedupe / merge  │
                 └───────┬────────┘
                         │
                         ▼
                 ┌────────────────┐
                 │ Canonical Store│
                 │ + derived index │
                 └───────┬────────┘
                         │
当前任务 ──▶ scope/filter/retrieve/rerank
                         │
                         ▼
                 ┌────────────────┐
                 │ Context Builder │
                 └───────┬────────┘
                         │
                         ▼
                       Model
```

其中，Canonical Store 是可管理的事实来源，向量索引、全文索引和摘要是可重建的派生物。不应让向量库成为唯一副本，否则很难可靠实现更新、溯源和删除。

一个简化的读取接口可以长这样：

```python
def recall(query: RecallQuery) -> list[MemoryRecord]:
    allowed = store.filter(
        subject_id=query.subject_id,
        scopes=query.allowed_scopes,
        status="active",
        valid_at=query.now,
    )
    candidates = hybrid_search(allowed, query.text)
    consistent = resolve_conflicts(candidates)
    ranked = rerank(consistent, query)
    return fit_budget(ranked, query.token_budget)
```

这段伪代码的顺序很重要：先限定权限和作用域，再做语义检索；先解决过期与冲突，再将结果放入模型上下文。

## 如何评估记忆系统

完整评估应沿生命周期拆开：

| 环节 | 关键问题 | 可观测指标示例 |
| --- | --- | --- |
| 写入 | 该记的是否被记住，不该记的是否被拒绝？ | 写入 precision / recall |
| 规范化 | 重复和冲突是否被正确合并？ | 重复率、冲突解决正确率 |
| 召回 | 需要的记忆是否进入候选集？ | Recall@K、MRR |
| 注入 | 关键记忆是否在预算内被保留？ | 上下文覆盖率、token 成本 |
| 使用 | 记忆是否真正改善了决策？ | 任务成功率、约束违反率 |
| 安全 | 是否发生跨用户召回或敏感信息暴露？ | 泄漏率、权限拒绝正确率 |
| 遗忘 | 失效和删除是否覆盖所有派生物？ | 删除完整率、过期命中率 |

端到端测试不应只问“模型还记得吗”，还要包含这类对抗场景：

- 用户更改了旧偏好；
- 两个项目中存在同名但含义不同的对象；
- 外部文档包含企图改变 Agent 行为的指令；
- 相似度很高的旧记忆已过期；
- 用户要求删除记忆后，索引、摘要与缓存仍存在副本。

## 从多少复杂度开始

记忆系统应该随产品需求增长，不必一开始就建立一个包含知识图谱、多路召回和 LLM 重排的平台。

### 只有短对话

保存完整消息，按 token 预算保留近期历史即可。

### 需要恢复长任务

增加结构化任务状态、checkpoint 和可追溯的会话历史。这一阶段的核心是可恢复，不是语义检索。

### 需要跨会话个性化

引入有 subject、scope、source 和有效期的语义记忆，先支持用户显式写入、查看、纠错和删除。

### 需要利用大量历史经验

再为情节记忆增加全文或向量索引、混合召回、重排与系统化评测。

这个顺序强调一件容易被忽略的事：向量检索是扩展某类记忆的手段，不是 Agent 记忆的起点。

## 结语

记忆并不存在于 Agent 架构的某一个箱子里。它横跨模型上下文、会话历史、任务状态、外部存储、检索索引和权限系统。

一个可靠的记忆系统，不仅要记得多，还要：

- 只写入值得长期保留的信息；
- 始终带着用户、作用域、时间和来源；
- 在正确的任务中被召回，在有限预算内被准确表达；
- 面对冲突、过期和更正时能够演化；
- 面对隐私和安全要求时能够解释、限制与删除。

> **真正的长期记忆不是“永不遗忘”，而是让有效信息在需要时出现，让失效信息在不再成立时退场。**
